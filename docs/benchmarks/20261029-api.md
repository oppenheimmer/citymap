# Overpass request protection, 2026-10-29

This work reduces request bursts and retry amplification. It does not establish
faster cold Overpass queries or a lower real-world rejection rate. All provider
tests use local mocks; no public Overpass traffic was generated for validation.
The separate [rendering measurements](20261029-rendering.md) measure local CPU
and drawing behavior, not upstream query performance.

## Changed behavior

- A transient HTTP 500 keeps combined cells together and backs off, instead of
  immediately retrying each cell separately. Untouched cells wait during an
  outage too. A later failure cannot shorten an existing cooldown.
- Public-provider viewport requests share one queue per provider origin across
  maps and same-origin tabs. Successful downloads return before a bounded
  elapsed-time-based pause. Shared failures preserve backoff and Retry-After.
- A reservation saved before dispatch survives reload. Aborting an issued query
  keeps its reservation because browser cancellation does not establish that the
  upstream server has stopped computing. Cancelling queued work sends nothing.
- Browser-cache reads bypass the queue. Fully cached views remain available even
  while another tab holds an unanswered network request.
- A downloadable load report records lifetime dispatched-request totals, cache
  hits, timings, queue waits and the most recent 20 failures, including HTTP status
  where available. It excludes queries, coordinates, provider response text and
  URL credentials/paths/query strings.

## Reproducible evidence

`tests/live-scheduler.test.ts` proves outage waits and unchanged retry batches
with a controlled clock. `tests/live-provider-pacer.test.ts` independently covers
the shared queue, cancellation, stored reservations and unavailable browser APIs.
`tests/live-viewport-units.test.ts` checks bounded reports and request totals
across explicit retries.

`tests/local/live-viewport.spec.ts` uses the real cells worker, Web Locks,
IndexedDB and a local HTTP provider. The provider records request timestamps.
The cases verify:

| Scenario | Assertion |
| --- | --- |
| One HTTP 500 on a four-cell request | Only one initial request during backoff; the retry query is identical; a downloaded report names HTTP 500. |
| Two tabs, one unanswered query | The second tab sends no request; cancelling it sends nothing; a third fully cached tab becomes ready. |
| Provider asks for five seconds, then page navigates | The next query arrives at least 4,950 ms after the rejected query; a new map cannot reset the wait. |
| Local storage denied | Subsequent query start times remain at least 1,000 ms apart. |

Focused V8 coverage of the scheduler, viewport and pacer unit files gives 100%
line / 87.5% branch coverage for `provider-pacer.ts`. Native browser coordination
is covered by the browser cases, not by that unit percentage.

The final milestone passed 251 unit tests, all 93 local browser cases and all 10
built-app browser cases. Svelte/TypeScript checks, lint, generated-data validation,
the normal production build and offline deployment checks passed. The complete
browser gate ran with application source fixed; it includes rendering/export
parity, cache clearing, real Monaco data, default viewport loading and the
whole-area rollback path. No runtime dependencies were added.

## Limits and later work

Coordination covers viewport requests within one app origin and browser profile;
it is not a global/IP-wide queue. Without Web Locks, only in-page serialization
is available. Denied storage prevents reload persistence. A cancelled four-cell
query can defer the next uncached request for up to 110 seconds. The whole-area
rollback path remains separate. See [live-road behavior](../LIVE_ROADS.md).

The next data-reuse milestones are bounded older-cache fallback during outages
and persistence of completed split cells. Query-geometry cropping needs decoder
and seam regression checks before use. Prepared R2 publication remains limited
to Monaco; no new datasets or infrastructure were published.
